# mngment.ru — инструкции для Claude

Статический сайт (GitHub Pages, см. [README.md](README.md)). Деплой — прямой пуш в `main`.

## Автопуш

После любой правки на сайте — сразу `git add` + `git commit` + `git push origin main`, не дожидаясь отдельной просьбы. Не оставлять изменения только в рабочей копии «на потом» и не спрашивать разрешение на пуш каждый раз — это уже разрешено по умолчанию для этого репозитория.

Если правку делает другая параллельная сессия и её изменения ещё не закоммичены — не приписывать их себе и не смешивать в одном коммите со своими: закоммитить только свою правку (при необходимости — точечно, по гранкам/hunk'ам), оставив чужую незакоммиченную работу в рабочей копии как есть, для той сессии.

## Обязательная проверка перед каждым изменением

Любая правка на этом сайте (контент, дизайн, техника, конверсионные страницы) должна пройти чек-лист из [правила/правила-проверки-изменений-на-сайте.md](правила/правила-проверки-изменений-на-сайте.md), прежде чем деплоиться в `main`.

Порядок работы:
1. Определить тип изменения (контент / дизайн / техническое / конверсионная страница) — в файле под каждый тип свой блок правил.
2. Пройти **базовые правила** (раздел 🔒) — они обязательны всегда, независимо от типа.
3. Пройти правила своего блока.
4. Проверить стоп-факторы (раздел 🚫) — если хоть один сработал, откатить или доработать, не деплоить.
5. Если есть быстрый способ проверить программно (curl на SSR-контент, grep на дубли title/canonical, наличие Schema-блока) — сделать это самостоятельно, не полагаясь только на память.
6. Что нельзя проверить автоматически (PageSpeed, консоль браузера, поведение на реальном телефоне, Rich Results Test) — явно сказать пользователю, что нужно проверить вручную, а не считать сделанным.

Не пропускать этот процесс даже для мелких на вид правок — правила рассчитаны именно на «быстрые» изменения, которые незаметно ломают SEO/GEO/конверсию.

## Написание новых статей в блог

Любая просьба вида «напиши статью», «добавь статью в блог», «нужен материал про...» — это запрос на статью для блога mngment.ru. **Обязательно** прочитать [правила/методология-написания-статей-для-блога.md](правила/методология-написания-статей-для-блога.md) целиком, прежде чем писать хоть одну строчку, и следовать ей, а не писать «как получится».

Порядок работы:
1. Прочитать методологию, если она ещё не в контексте этой сессии.
2. Привязать тему к одной услуге из таблицы в методологии — без этого статью не начинать.
3. Собрать структуру по скелету из методологии (лид-абзац с прямым ответом, H2/H3 с самодостаточными тезисами, конкретика, FAQ при подходящем формате).
4. Технический head-блок и JSON-LD собрать по шаблону из методологии (копировать из существующей статьи, не с нуля).
5. Выполнить шаги публикации из методологии (sitemap.xml, blog/index.html, при необходимости llms.txt, внутренние ссылки).
6. Прогнать готовую статью через чек-лист [правила-проверки-изменений-на-сайте.md](правила/правила-проверки-изменений-на-сайте.md), раздел «Изменение контента» — это отдельный шаг, методология его не заменяет.

Не пропускать пункт 1 даже если тема кажется простой — именно на «быстрых» статьях без методологии теряется GEO-цитируемость и связка с услугой.

## Цели в Яндекс.Метрике при добавлении нового функционала

Счётчик Mngment.ru — **111721939**. Полный реестр целей (автоцели + ручные JS-события с параметрами) и что каждая ловит — [правила/цели-метрики.md](правила/цели-метрики.md).

Если правка добавляет новый кликабельный/конверсионный элемент (кнопка, CTA-ссылка, форма, модалка, виджет) — сверяться с реестром: подпадает ли он под существующий селектор (например, любая новая `.btn-primary` уже попадёт в `cta_click` без доработок) или это принципиально новый тип действия.

Если новый тип действия не покрыт реестром:
1. Сообщить об этом явно в ответе пользователю.
2. Добавить `trackGoal('<событие>', {...})` в script.js рядом с обработчиком клика, задеплоить.
3. Обновить таблицу в [правила/цели-метрики.md](правила/цели-метрики.md) новой строкой.
4. Отправить письмо на **send@mngment.ru** через MCP-инструмент `timeweb-mail` (тема «Новая цель Метрики: <название>», в теле — какой элемент, какой event/параметры, напоминание вручную завести цель в интерфейсе Метрики).

Не пропускать пункт 4 даже для мелких на вид правок — иначе цель есть в коде, но не в интерфейсе Метрики, и конверсия нигде не считается.
